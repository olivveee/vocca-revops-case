# Vocca · Senior RevOps case study

Work for Part 1 of the Vocca Senior RevOps case: **1A**, a sales efficiency dashboard, and **1B**, mapping the TAM ([`docs/tam_mapping.md`](docs/tam_mapping.md)).

- **Google Sheet (the deliverable and the back-office):** https://docs.google.com/spreadsheets/d/15gDvbv-UHpQrvqLaG8rC6UI93rJtEb1nnbNSiZPjwug/edit
- **Web view:** https://vocca-revops-case.vercel.app/ (source in `web/`), a read-only visual layer on top of the same sheet.
- **TAM slides (1B):** https://vocca-revops-case.vercel.app/slides.html: four slides in French (what is wrong, the model, the build, recommendations), arrow keys to navigate, figures read from the same script output.
- **TAM cockpit (1B):** https://vocca-revops-case.vercel.app/tam.html: a work tool, not a dashboard. Work queues (duplicates, missing identity, hierarchy, market, contacts) open onto the detailed list of records, filterable by creator, market and type and exportable as CSV; a quality-by-source view shows which tool creates the mess; the pair review records merge / keep-separate decisions. Its data and the downloadable action pack (`web/data/tam_action_pack.xlsx`) are generated by `scripts/tam_dedup.py`.

## How the pieces fit

```
Attio export (CSV)  ->  Google Sheet  ->  web page
                        RAW_*           (reads DEALS_CLEAN, RAW_team, WEB_PARAMS
                        DEALS_CLEAN      published as CSV; no business rule lives here)
                        PARAMS
                        CALC
                        DASHBOARD
                        WHAT_WORKS
                        DATA_QUALITY
```

- **The sheet owns everything:** raw data, cleaning rules (`DEALS_CLEAN`, all `ARRAYFORMULA`s), the recalibrated quota, the thresholds (`PARAMS`). Change a quota or a threshold there and both the `DASHBOARD` tab and the web page follow.
- **The web page only displays.** It fetches three published tabs at load time, so a change in the sheet reaches the page once Google republishes (a few minutes).
- **The Python scripts were exploration only:** they profiled the export and sized the data-quality issues before anything was built. No dashboard number is computed in Python.

## Metrics, and what was left out

The web page reads top-down, from the country to the AE, with four filters: country of the account, period (month, last 3 months, year to date), month, and deals (all, new logo, expansion).

1. **Are we on track?** Four numbers: new-logo ARR vs quota (group rollouts counted as expansion), expansion ARR, weighted healthy pipe, win rate with the July bulk clean-up counted as losses. Then the 12-month new-logo trend and the open pipe by stage with its unhealthy share (older than 90 days, or next step / expected close more than 30 days late).
2. **What works?** Won ARR, win rate and open deals by source and by specialty.
3. **Who needs help?** One line per AE, five columns: new-logo ARR vs quota, win rate, healthy pipe, flags.

Amounts are in one reporting currency, USD by default: deals come in EUR (1,469) or USD (37) and are converted at the live EUR→USD rate (Google Finance), or at a fixed rate typed in `PARAMS`. Country is the account's, not the AE's: the French team owns almost every deal, US accounts included. The quota is compared with what the country's own team signed. The Sheet's `WHAT_WORKS` tab holds the same breakdowns in formulas; account country, source and cleaned specialty are columns of `DEALS_CLEAN`.

Left out on purpose: sales cycle length (deals are created late, often at signature), the AEs' closing probability (half empty, uncalibrated), activity volume (not in the export), SDR metrics (demo attribution is broken). The `README` and `DATA_QUALITY` tabs of the sheet explain each choice.

**Quota:** the synthetic quotas put every AE at 150-600%, so they were replaced by the median monthly new-logo ARR of tenured AEs over the last 6 complete months, with a 25/50/75/100% ramp-up. A top-down quota can be typed in `PARAMS` and overrides it. `PARAMS` > Quota used switches to the provided synthetic quotas, per AE and without ramp-up, to compare: the team then sits at about 260%.

## Running the scripts

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/profile.py data
.venv/bin/python scripts/checks_deals.py data
.venv/bin/python scripts/checks_accounts.py data
.venv/bin/python scripts/checks_extra.py data
.venv/bin/python scripts/metrics_test.py data
.venv/bin/python scripts/tam_dedup.py data out/tam web/data   # also refreshes the TAM cockpit and action pack
```

## Running the web page locally

```bash
python3 -m http.server 4173 --directory web
```

Then open http://localhost:4173. The page reads the published sheet configured in `web/config.js`.

## Deploying on Vercel

Import the repository in Vercel and set **Root Directory = `web`**. No build command, no output directory: it is a static site. `web/vercel.json` sets `X-Robots-Tag: noindex`.

## With a week and a warehouse

- Fix the source, not the report: mandatory `signed_date`, `signed_arr` and `loss_reason` at Closed Won / Lost in Attio, `close_date` no longer used as an expected date, next steps enforced on open deals, group rollouts typed correctly at creation.
- Sync Attio to the warehouse daily and move the `DEALS_CLEAN` rules into a tested SQL / dbt model; the sheet or a BI tool reads the final table.
- Use stage-change history for a real funnel and cycle time, and calibrate stage weights on observed conversion.
